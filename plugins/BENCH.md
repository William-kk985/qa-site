# 体积基准：小任务 vs 中型任务（**堆**就是那个拐点）

一句话结论 —— **「Rust 比 MoonBit 小」只在不用堆的时候成立。**

`plugins/README.md` 那张「体积参考」测的是一个**小任务**（纯数字、零分配），
量出来 Rust 274 B 最小。但那个任务根本不碰堆，所以它量不出**运行时**的成本。
一旦要分配内存，同一个中型任务上：

|  | 小任务（零分配） | 中型任务（要分配） |
|---|---|---|
| **C** | 268 B | 591 B（栈上固定数组，还是不碰堆） |
| **Rust** | **274 B** | 533 B（栈上固定数组）→ **15234 B**（`Vec`） |
| **MoonBit** | 473 B | **4308 B**（`Array`，走 GC 堆） |

小任务上 Rust 最小；中型任务上一动堆，Rust 是 MoonBit 的 **3.5 倍**。
两个数字都是实测（来源见下面两张表）。

> ⚠️ 但**别为体积挑语言** —— 512KB 的插件上限面前，15KB 也只有 3%。往下看。

## 怎么跑

```bash
bash plugins/bench-size.sh
```

工具链不在 PATH 里时用环境变量指路（和 `build.sh` 同一套风格）：

```bash
CLANG=/usr/lib/llvm-14/bin/clang \
WASM_LD_DIR=/path/to/lld14/usr/lib/llvm-14/bin \
CARGO=/path/to/.cargo/bin/cargo \
MOON=/path/to/.moon/bin/moon \
bash plugins/bench-size.sh
```

脚本会编出四种实现、**验证四个产物输出逐位相同**（`hot_score(1,2,100,3)`
必须都等于 `12.727272727272727`，不一致就报错退出），再打出体积和段结构表。
没装的工具链会跳过并告诉你怎么装；需要 `node` 来做那道一致性校验。

- 源码在 `plugins/bench/`（`c/`、`rust-fixed/`、`rust-vec/`、`moon/`）
- 编出来的 `.wasm` 落在 `plugins/bench/.out/`，**不提交** —— 这个基准和
  `prebuilt/` 不一样，它的产物只是实验读数，谁想看跑一遍就能复现

## 表 1：同一个中型任务，四种实现

任务：堆分配 + 插入排序 + 聚合，签名都是 `hot_score(votes, answers, views, age_days) -> f64`。
本机实测（`bash plugins/bench-size.sh` 的输出）：

| 变体 | 体积 | 段结构 |
|---|---|---|
| Rust 固定数组 | 533 B | `code=460` `data=0` |
| C 固定数组 | 591 B | `code=519` `data=0` |
| **MoonBit `Array`（GC 堆）** | **4308 B** | `code=4023` `data=24` |
| **Rust `Vec`（堆分配）** | **15234 B** | `code=14038` `data=998` |

四个产物的 `hot_score(1,2,100,3)` **逐位相同**，都是 `12.727272727272727`
—— 这是"同一个算法、不同实现"的唯一证据，脚本每次都会重验。

## 表 2：为什么会这样 —— 运行时是什么时候被触发的

「体积」不是一个数，是**代码段 + 静态数据段**的和。拆开看，拐点在哪一目了然：

| 实现 | 体积 | code | data | 链接了什么运行时 |
|---|---|---|---|---|
| Rust 固定数组 | 533 B | 460 | 0 | **无**。`[f64; 256]` 在栈上 |
| C 固定数组 | 591 B | 519 | 0 | **无** |
| MoonBit `Array` | 4308 B | 4023 | 24 | **自带的 GC 运行时**（紧凑，自带分配器） |
| Rust `Vec` | 15234 B | 14038 | 998 | **dlmalloc + panic 机制 + `core::fmt` 格式化代码** |

- **小任务 / 固定数组（C、Rust-fixed）**：函数只吃 `f64`、返回 `f64`，
  没有一次分配、没有一条 panic 路径。于是编译器能把整个程序约简成几百字节，
  连 `memcpy` 都不需要 —— `data=0` 就是这个意思。**不用堆，就不链接任何运行时。**
- **Rust `Vec`**：`Vec::with_capacity` 需要 `__rust_alloc` → 默认全局分配器
  dlmalloc；`v[i]` 的越界检查会 panic → panic 机制；panic 消息要格式化 →
  `core::fmt`。这三块是**一起**被拖进来的，`code` 从 460 B 涨到 14038 B（约 30 倍），
  `data` 从 0 涨到 998 B。**这就是 Rust 那 15KB 的来源。**
  （这三块各自占多少，本基准没有逐块拆开量 —— 想拆得再各编一版。
  但"堆是拐点"这个量级结论不依赖这个拆分。）
- **MoonBit `Array`**：同样要分配，但它用的是**自带的 GC 堆**，不链接系统分配器、
  不链 `fmt`，所以只扛一个 4KB 的紧凑 GC 运行时。

> ⚠️ 一个容易看错的点：**`data` 小 ≠ 不用堆**。堆是运行时向 `memory` 申请的那块，
> 不落在 `data` 段里。Rust `Vec` 的 `data=998` 也不是"堆"，是分配器结构和 panic 消息表。
> 判断有没有链进分配器，要看 `code` 段。

## 老实说：这不是通用基准

- 这是**我方的一个中型任务、一个数据点**（分配 + 插入排序 + 聚合）。换个任务、
  换个规模（比如分配次数多十倍、或者要做字符串处理），数字都会变。
  它想证明的只是一件事：**堆是一个数量级的拐点**，不是"语言 X 比语言 Y 好"。
- **15KB 离插件 512KB 的上限还很远**（约 3%）。所以就这个站的用途而言，
  上面这些数字**不该影响你选语言** —— 选你最顺手的那门。真要在意体积，
  该在意的是"有没有链接进一整个运行时"，而不是 268 B 和 274 B 谁多 6 字节。

### Rust 的 15KB **不是硬下限**

换 `wee_alloc` 之类的小分配器、或者上 `#![no_std]`（连默认的 `core::fmt` panic
路径一起绕开）都能把这个数字压下去。**但那是要手动配置的 opt-in** ——
而 MoonBit 那份什么都不用配，就是 4KB。这才是两者真正的区别。

> ⚠️ **我们没有 wee_alloc 的实测数字，所以这里一个数都不给。**
> 试过，但这台机器的代理拦了 crates.io 的 TLS，依赖根本没拉下来
> （构建后 `Cargo.lock` 里没有 `wee_alloc` 条目）。
> 如果你在哪儿看到一个和 `rust-vec` **字节完全相同**的 "wee" 产物，那是假的：
> 它是上一次构建的残留，不是一次成功的 `wee_alloc` 编译。
>
> 想补这个数据点：网络能到 crates.io 的机器上，给 `bench/rust-vec` 加上
> `wee_alloc` 依赖 + `#[global_allocator]`，重跑一次即可。
